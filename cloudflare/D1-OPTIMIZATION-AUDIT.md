# D1 Usage Audit

## Findings before optimization

- `js/platform.js` caches and deduplicates public-bootstrap data in page memory for 10 seconds. Its pagination loop requests the whole `/public/bootstrap` response again at each offset. `cloudflare/worker.js` runs 12 D1 statements for every such response (10 collections, a separate match-scorer-events statement, and payment settings), so a long collection causes all those reads to repeat on every page.
- `/public/standings` in `cloudflare/worker.js` performs four reads per request: tournament visibility, group results, league participants, and league match results. It recalculates tables from match records on every request.
- `updateMatchResult` validates each recorded player scorer with its own D1 lookup. With up to 99 scorer entries per side, this can issue up to 198 player reads for one result submission.
- Manager and Admin bootstrap routes are authenticated and scope-filtered. They load related collections in grouped queries rather than an obvious per-row N+1 loop, but several use `SELECT *`; changing those projections risks breaking existing dashboard data contracts.
- Public API responses default to `Cache-Control: no-store`. The configured API host in `js/platform-config.js` is a `workers.dev` hostname; no Wrangler config or shared cache/KV binding is present. The Worker public bootstrap can include payment settings, so it is not a candidate for shared response caching. Fixtures poll every 60 seconds when there are no live matches and every 15 seconds while live; match-centre pages poll scheduled matches every 60 seconds and live matches every 15 seconds. Hidden pages do not continue polling.
- Existing migrations include indexes for the main registration, match, player, and event access patterns. There is no configured D1 database, so `EXPLAIN QUERY PLAN` was checked against an in-memory SQLite database built from the migrations. The stage-linked match lookup used the broader public-match index before the new migration.

## Implemented changes and expected impact

1. Keep full bootstrap responses available for legacy callers, but have `requestAll` pass its allowlisted collection selection on the initial request too. Public pages request only the collections they use; registration and pending-manager views opt into payment settings explicitly. A selected collection uses one D1 statement, or two when matches are selected because scorer events are also loaded. Continuation pages request only collections that were full on the previous page.
2. Fetch all registered scorer IDs for each scoring team in one parameterized query, then validate the original entries against those results. This changes the scorer-validation read count from one per scorer to at most one per team (two per result).
3. Combine league participants and completed match records with `UNION ALL`, keeping one row per participant and one row per match rather than multiplying matches across participants. Accumulate the same scores and ranking rules. This reduces the standings route from four D1 statements to three without increasing result-row cardinality. Migration `0011_optimize_stage_standings.sql` adds `(stage_id, published, status, kickoff)`; a stage-first query plan uses the new index instead of `afc_matches_public_idx`.
4. Add a bounded, isolate-local cache for anonymous `/public/standings` GET responses only (15 seconds, at most 64 entries and 128 KiB per response). Errors and requests with Authorization/Cookie headers bypass the cache; successful related admin writes invalidate the local cache. Since isolate memory is not shared across workers or data centers, the 15-second TTL also bounds stale responses after mutations on another isolate. Public bootstrap responses remain uncached; the configured host has no shared edge cache or cache/KV binding. Public media stays public-only and its browser cache lifetime is reduced from 60 minutes to 10 minutes to limit stale visibility after unpublishing.
5. Narrow public bootstrap requests for the homepage, public content pages, registration, and manager dashboards. Filtered requests skip payment-settings reads unless explicitly requested, and paginated payment-enabled requests fetch settings only on the first page.
6. Reduce scheduled match-centre polling to 60 seconds, retain 15-second refreshes for live matches, and stop scheduling refreshes while the document is hidden.

The configured `workers.dev` host has no zone-backed Cache API, and there is no KV/cache binding or Wrangler manifest. The standings cache therefore uses bounded Worker-isolate memory rather than a shared edge cache. Derived standings remain calculated from authoritative match records; no derived data is persisted.

## Verification and limits

- Browser-runtime checks verified 12 D1 statements for the full bootstrap, 3 for a `teams,matches` continuation page, the standings cache hit/expiry/auth/error/invalidation behavior, and frontend continuation-page merging. The prior standings reducer also passed its ranking check before the final `UNION ALL` row-shape refinement.
- In-memory SQLite loaded the project migrations, executed the exact final `UNION ALL` standings query, and ran `EXPLAIN QUERY PLAN`. The query returned one row per participant plus one per match (4 rows for the 3-team/1-match fixture); after migration 0011, the match lookup uses `afc_matches_stage_public_status_idx(stage_id, published, status)` instead of the broader `afc_matches_public_idx(published, status)`.
- These are query-statement counts and a schema-only query plan, not production measurements. D1 rows read/written, actual request volumes, and deployed-cache hit rates were not available and are not claimed. Scorer validation is now at most two D1 reads per result (one per scoring team) rather than up to 198; this is a bound from the input validation limits, not a production measurement.
- The repository's Node tests use `node:test`, but Node.js is not installed in this environment, and the integrated browser disconnected before the final standings reducer refinement could be rerun. The final SQL/query plan was verified separately, but the optimization tests (including the new filtered-bootstrap cases) and final JavaScript reducer still need execution. Run `node --test cloudflare/tests/*.test.mjs` in a Node-enabled environment before deployment.
